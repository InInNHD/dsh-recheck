# Recheck：插件生态调研与后续版本计划

调研日期：2026-10-04。当前基线：Recheck `0.1.0-alpha.4`，已公开发布；已声明支持的宿主为 DeepSeek Harness `0.2.0-rc.2`。本文是后续开发建议，列出的新功能和新宿主兼容性尚未实现、验收或发布。

建议路线：**alpha.5 兼容与诊断 → alpha.6 录入效率 → beta.1 复核队列 → 0.1.0 稳定发布 → 0.2.0-alpha.1 精准依据实验（满足需求门槛后启动）**。

## 1. 调研范围与结论

通过 GitHub 连接器查询相关仓库，阅读 README、Release、近期提交、Actions 结果和代表性 Issue/PR，并对照本项目源码、现有 CI 与验收文档。选取六个功能或维护方式与 Recheck 有直接关系的社区插件；这是一组定向样本，不是整个插件生态的排名或完整统计。

最值得采纳的结论：

1. **先维护明确的兼容组合。** 宿主仍处于预发布阶段，插件可安装不代表 Host、Client 和真实文件权限链都能工作。新宿主必须通过实际安装包验收后才能加入支持清单。
2. **降低保存结论和复核的操作成本。** 原生入口、明确的依据选择、状态筛选、来源会话导航，比增加独立工作流引擎更适合 Recheck。
3. **把真实宿主生命周期纳入回归。** 插件关闭、会话切换、迟到响应、样式卸载以及其他插件的覆盖层，都可能是普通单元测试发现不了的问题。
4. **保持产品边界。** Recheck 的价值是发现依据变化、保留主动复核记录。会话地图、上下文分析和团队调度已有独立插件；现阶段不再实现一套。
5. **精细依据需要用户反馈证明价值。** 当前整文件指纹适合简单可靠的第一版；只有确实出现较多无关改动提醒，才进入片段依据实验。

证据口径：仓库功能介绍表示作者声明；Actions 结果只证明对应工作流、分支和提交的结果；Issue 中的事故描述表示报告者反馈。本次没有在本机逐个安装或运行这六个插件，不能据此宣称它们均兼容用户当前客户端。下文日期均按 GitHub 原始 **UTC** 日期列出，避免跨时区混淆。

### 2.1 可直接借鉴的维护案例

**案例 A：兼容清单必须跟实际发布的宿主一致。** AgentTeams `v0.1.22` 将推荐目标明确为已经发布的 `0.2.0-rc.2`，区分旧版本和预览渠道。Recheck 可采用更小的清单：当前已验证宿主，加一个正在验证的候选宿主；不需要承担同样数量的历史版本。来源：[兼容清单](https://github.com/NanmiCoder/dsh-agent-teams/blob/9cba4fe4171f27c019991cafd2a107f87ef3517b/compatibility.json)、[v0.1.22](https://github.com/NanmiCoder/dsh-agent-teams/releases/tag/v0.1.22)、[main Verify](https://github.com/NanmiCoder/dsh-agent-teams/actions/runs/36577736541)。

**案例 B：普通模拟对象可能掩盖真实服务行为。** dsh-context 的 Issue #108 报告了 tracked Proxy 与清理逻辑的差异，`v0.62.3` 发布说明记录了修复和真实服务回归；PR #106 处理旧请求在状态重建后迟到的问题。Recheck 不使用同一归因 Hook，不能据此认定存在同一漏洞，但应验证自己的注册、取消和跨会话结果隔离。来源：[Issue #108](https://github.com/bowenliang123/dsh-context/issues/108)、[v0.62.3](https://github.com/bowenliang123/dsh-context/releases/tag/v0.62.3)、[PR #106](https://github.com/bowenliang123/dsh-context/pull/106)。

**案例 C：自动投影的成本会随会话规模增长。** Synapse 的 Issue #26、#27 和关联 PR 描述了全量保存、请求放大、迟到消息重新打开页面等问题；PR #32 的适配在调研时仍未合并。这些是公开反馈和待审方案，不是本次独立复现的结论。对 Recheck 的启示是保留显式操作、有界读写，避免为“自动收藏”常驻监听全部消息。来源：[Issue #26](https://github.com/liangmianya/dsh-synapse/issues/26)、[Issue #27](https://github.com/liangmianya/dsh-synapse/issues/27)、[PR #28](https://github.com/liangmianya/dsh-synapse/pull/28)、[PR #32](https://github.com/liangmianya/dsh-synapse/pull/32)。

**案例 D：设置持久化要匹配宿主环境。** Boot Animation 的 README 描述了将选择保存在宿主目录，以及先读取宿主状态再决定播放的设计；其宽松依赖策略不能直接套用到承担文件读写和工具协议的 Recheck。优先借鉴设置归属和排错信息，继续保留 Recheck 的明确兼容约束。来源：[固定提交 README](https://github.com/NativeDog1/dsh-boot-animation/blob/15ff124ff85cd23177d9b14dc81fae5c24adb8dc/README.md)。

### 2.2 官方宿主的新变化

官方于 2026-10-03 发布了 [`dsh-v0.2.1-alpha.1`](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.1)。其中与本项目维护相关的变化包括：

- 修复切换插件时可能移除其他插件样式的问题。
- Desktop 默认使用系统分配端口；测试脚本不能继续把某一个端口当作通用事实。
- 插件入口与依赖映射、安装状态提示有所调整；替换已安装版本仍涉及重启要求。
- 部分扩展入口变化，并移除 invariant 插件及相关导出。

这些变更是**安排兼容验证的理由**，并不证明 Recheck 已经不兼容。当前 Recheck 没有直接使用被移除的 invariant 入口；仍需验证两端构建、服务注入、文件权限和真实安装流程。本文不建议直接升级用户日常宿主，也不提前放宽 peerDependencies。

## 3. Recheck 当前已经具备什么

当前能力以 [README](../README.md)、[UI 改版验收](15-ui-refresh.md)、[数据类型](../src/types.ts)、[业务处理](../src/recheck.ts) 和 [CI](../.github/workflows/ci.yml) 为准：

- `create/list/get/edit/check/review/archive/export` 八类操作，原生右侧栏及 Agent 工具入口。
- 文件新鲜度与复核意见分开；检查不等于复核，依据未变化不等于结论正确。
- 单卡/全部活动卡片检查、只读临时检查、历史、归档恢复、Markdown 导出。
- 标题和结论搜索、新鲜度筛选、需要关注筛选；列表已有“需要关注优先”的默认排序。
- alpha.4 已完成主题变量、紧凑布局、表单分组、字数提示和窄栏适配。
- 项目本地 schema 1 存储、原子写入、版本冲突保护；不保存依据正文，不依赖外部业务服务。
- 已有 Windows/Ubuntu CI、29 项核心及真实 SDK 测试、实际 tgz 生命周期检查、Web 回归，以及 Windows Desktop 人工/脚本验收记录。
- 已有 npm alpha、GitHub Release、相同安装包校验、安装回退文档和贡献入口。

因此，下一阶段是补充兼容组合和特定行为回归，而不是重新建设以上已有能力。本次只核对现有记录，没有重新运行这些功能测试。

仍有明确的体验空间：依据主要靠手填路径；复核意见不能作为列表筛选条件；检查范围主要是单卡或全部活动卡片；安装排错分散在文档里。草稿现在仅在客户端内存中，刷新或关闭会丢失。

## 4. 总体版本路线

| 建议版本 | 主要目标 | 必须交付 | 估计工作量 | 数据兼容 |
| --- | --- | --- | --- | --- |
| `0.1.0-alpha.5` | 升级可验证、故障可定位 | 精确兼容清单、加载诊断、生命周期与共存验收 | 3–5 人日 | 保持 schema 1 |
| `0.1.0-alpha.6` | 更容易保存和找到依据 | 路径逐项反馈；可用时接入宿主文件选择、来源会话导航 | 4–6 人日 | 保持 schema 1 |
| `0.1.0-beta.1` | 高效处理待复核结论 | 意见筛选、可选排序、选定卡片检查、明确的复核步骤 | 4–7 人日 | 保持 schema 1；扩展请求协议 |
| `0.1.0` | 可持续使用的稳定基线 | 试用反馈收敛、回归、备份恢复演练、明确支持范围 | 3–5 人日，另需至少一周试用 | 保持 schema 1 |
| `0.2.0-alpha.1`，有条件启动 | 减少无关改动提醒 | 有界片段依据原型和迁移验证 | 5–8 人日原型；产品化另估 | 预计 schema 2，先设计再编码 |

人日是单维护者熟悉项目并有开发辅助时的粗估，不是交付日期。前四阶段合计约 14–23 人日；按业余投入另行折算日历时间。试用可与缺陷修复交叠。兼容验证失败、公开 SDK 缺少能力或试用结果不达标时调整范围，不为保持版本表而发布。

发布编号也不是固定日历：如需独立热修复，可以插入后续 alpha/beta 或稳定版补丁；已经发布的编号、tag 和安装包不得替换。

## 5. 各版本执行与验收

### 5.1 alpha.5：兼容性、加载诊断与共存

**用户得到什么：** 能知道当前运行的插件版本、宿主组合是否经过验证，以及安装后为什么还没有生效。

执行顺序：

1. 增加一份小型兼容清单，区分“已验证”“候选”“未验证”。从 `0.2.0-rc.2` 基线和 `0.2.1-alpha.1` 候选开始；分别记录平台、Desktop/Web、插件提交、安装包哈希与验收报告。不要先搭建通用兼容框架。
2. 扩展现有实际 tgz 测试，验证候选宿主的 Host 注册、Client 注入、原生侧栏、真实 FS/沙箱和安装卸载重装。根据结果选择支持第二组合或明确暂不支持；失败时继续维护现有组合。
3. 在折叠的“版本与诊断”区域展示客户端构建版本、Host 端插件版本、可读取到的宿主版本、读写能力与 schema 状态。安装管理器中的版本如无公开查询接口，显示“无法读取”，不能拿加载版本冒充安装版本。profile 不可查询时同样不猜测。
4. 将已有拒绝码映射为简明行动：版本冲突建议重新读取；无权限说明只读能力；损坏存储说明保留原文件及恢复入口。诊断复制内容默认不包含结论正文、依据正文、密钥和本机绝对路径。
5. 回归开关插件、切换会话、离开页面后迟到响应以及中途取消。与用户已安装的启动动画插件共存时，在覆盖层真正消失后检查可见内容、焦点和截图，不只判断 DOM 已挂载。

验收条件：

- 已支持组合的现有 `check`、实际包生命周期和 Web/Desktop 关键流程通过；新组合逐项记录，未通过不进入支持声明。
- UI/Host 版本不一致能够辨识；普通用户可按提示完成一次排错，不需要阅读堆栈。
- 连续切换/开关至少 20 次后，工具、监听和请求没有累积注册；旧会话结果不能覆盖新会话。内存若测量，应记录方法和噪声，不能仅凭一次 RSS 数字宣称无泄漏。
- 保留其他插件时，Recheck 的主题、输入焦点、关闭与重开均正常；不主动提升为全屏最高层级。
- 数据 schema、指纹规则和复核语义不变；回退 alpha.4 后能读取原数据。

涉及文件：`src/index.ts`、`src/client.tsx`、必要的样式、现有 `scripts/*smoke.mjs`、CI 和兼容/安装文档。构建信息尽量复用现有版本来源，不增加运行时依赖。

### 5.2 alpha.6：依据录入与原生导航

**用户得到什么：** 建卡时更容易填对依据路径，保存失败后能直接找到需要修改的项。

必须完成：

- 将依据输入的反馈细化到每一项：空项、重复路径、超出 8 个、非法相对路径、文件不存在、大小超限或权限不足。前端只做轻量格式反馈，最终校验仍在可信 Host 端执行。
- 保留“每行一个路径”的批量粘贴方式；提交失败保留标题、结论和说明，焦点定位到相关错误，不要求重新填写。
- 明确区分“选择依据”和“保存时捕获指纹”；不能用选择时的旧结果替代提交时的安全读取。
- 沿用宿主控件、主题和 300px 窄栏，说明文字按需展开；继续检查键盘导航和中文输入法提交行为。

有公开 SDK 能力时纳入本版：

- 使用宿主提供的文件选择/引用入口，把明确选择的文件转换为项目相对路径；取消选择不改动表单。先做不超过 1 人日的能力核查；若接口不适用，交付路径反馈改善并记录限制，不自建全盘文件浏览器。
- 利用已有 `actor.sessionId` 增加“打开此次记录的来源会话”。这指向创建/编辑/复核行为所在会话，不冒充最初论据的原始消息。目标不可用时给出说明；不通过扫描会话日志或注入页面 DOM 补救。

验收条件：

- 在专用项目中完成新建、编辑、选择取消、错误修正和失败重试；中文、空格路径、路径逃逸及链接目标继续经过原有边界校验。
- 切换项目时，旧的文件选择结果不能写入新项目表单；所有持久 I/O 继续走宿主 `ctx.fs`。
- 新用户知道草稿何时会丢失。此次不增加默认磁盘草稿或 browser localStorage 持久化；若后续需要，应单独定义内容归属、保留期限和清除方式。
- 原有工具创建调用、内存草稿隔离和 schema 1 数据继续兼容。

涉及文件：`src/client.tsx`、`src/client-styles.ts`、必要的 Host 校验结果映射与 Web/Desktop 流程测试。复用 `cards.ts`、`io.ts` 的边界规则。

### 5.3 beta.1：待复核队列和明确的检查范围

**用户得到什么：** 找到需要处理的结论，检查其中一组，再逐项作出复核意见。

必须完成：

1. 增加复核意见筛选：尚未复核、支持、否定、不确定。保留现有新鲜度筛选；两种筛选可组合。“需要关注”规则保持不变，不把所有否定意见自动当作待办。
2. 在已有关注优先排序上增加“最近检查”“最近更新”等明确选项；从未检查的卡片要有固定位置，排序需要稳定的次级规则。
3. 增加显式选中卡片后检查的能力，按钮显示“检查选中的 N 张”；保留“检查全部活动卡片”并明确它不受筛选影响。改变筛选时清空选择或明确提示隐藏选择，本版优先采用清空选择。
4. 使用 Host 端有界批处理共享唯一文件读取，继续遵守现有数量、字节与时间预算。不得在客户端并行调用大量单卡检查绕过总预算。
5. 复核页清楚展示“检查依据 → 阅读依据 → 选择意见 → 保存”的状态；未保存的临时检查不能用于持久复核。错误、冲突和 unknown 给出具体原因，避免只剩一种告警颜色。

协议设计：新增检查范围前先确定显式卡片 ID 与 expectedRevision 列表的格式、去重和上限；保持现有 `scope: card/all` 行为。按当前操作规定拒绝不可处理的目标；发生单卡冲突、超时或取消时返回逐卡结果和保存情况，不宣称整个批次具有不存在的全局原子性。扩展请求类型、参数白名单、工具 schema 和 RPC 一起更新。

验收条件：

- 不同筛选组合、排序、选中/清空及归档视图行为一致；没有选中的卡片不会被误检查。
- 检查中修改或归档目标、共享依据去重、达到预算、中途取消和只读临时结果均有真实回归。
- 需要关注统计基于明确范围，能够区分整个项目数量、筛选结果数量和选中数量。
- 批量检查不会自动提交支持/否定意见，不增加模型调用或执行测试。
- schema 1 不变；旧请求仍有效，新客户端遇到旧 Host 时通过能力/版本检测关闭新操作，避免误发不支持的参数。

涉及文件：`src/types.ts`、`src/cards.ts`、`src/index.ts`、`src/recheck.ts`、`src/client.tsx` 和现有测试。卡片上限仍为 200，不预先引入搜索引擎、数据库或虚拟列表依赖。

### 5.4 0.1.0：稳定基线与试用收敛

**用户得到什么：** 一套支持范围明确、升级可回退、使用一周后仍可靠的版本。

这一阶段以修复和验证为主，不再加入主要功能。建议邀请 3 名真实试用者，每人使用一个真实项目至少一周；仅收集自愿提供的操作体验和问题，不默认上传结论、文件正文或遥测。

建议试用目标，尚未实测：

- 每人保存至少 3 条确实希望后续复核的结论，并完成至少一次“依据变化 → 检查 → 主动复核”。
- 当结论和依据已准备好时，多数建卡操作能在一分钟内完成；若没有达成，先确认障碍是路径输入、概念理解还是界面操作。
- 所有试用者能够区分“文件没变”和“结论被支持”。
- 记录无关文件改动造成的提醒次数，作为下一阶段是否需要片段依据的输入，不把小样本当作统计结论。

发布门槛：

- 数据丢失、越权读写、跨项目串数据、错误复核以及支持组合无法加载的问题全部清零。
- 完成创建、检查、复核、冲突处理、归档恢复、Markdown 导出，以及已有手动备份/恢复流程的演练。恢复结果必须检查实际文件，不能把旧检查结果解释为恢复后的即时验证。
- 本版实际安装包通过现有 Windows/Ubuntu CI；Desktop、主题、窄栏等验收单独列平台。没有测试的 macOS/Linux Desktop 不写“全面支持”。
- 安装、升级、卸载保留数据、回退均有准确说明；中英文 README 的版本、支持范围和安装渠道一致。
- 决定并核对 npm 渠道：预发布继续走 alpha/beta；正式版满足门槛后才进入 `latest`。插件正式版不意味着仍属预发布的宿主也变成正式版。

如果试用者不足或关键问题未解决，继续 beta；不靠改版本号代替验证。由于前面保持 schema 1，稳定版不应夹带隐式数据迁移。

### 5.5 0.2.0-alpha.1：片段依据实验，有条件启动

**启动条件：** 至少 2 名试用者能给出重复出现的“文件其他部分修改、结论实际依据未变”的例子，且问题无法通过改选较小的依据文件解决。未达到条件时，优先维护 0.1.x，延期此版本。

原型范围：

- 保留整文件依据为默认方式；新增由用户明确选择的有界文本片段。
- 先限定 UTF-8 文本、明确的定位信息与片段字节指纹；定义编码、换行、范围变化和定位失败的规则。行号移动、重复文本或歧义时返回 unknown 并让用户重新绑定，不进行模糊匹配后自动宣称未变化。
- 最小原型可接受片段移动后需要重新选择；先证明减少提醒的价值，再决定是否增加安全的重新定位。
- schema 2 必须能明确区分整文件与片段依据，不能重新解释 schema 1 已有指纹。旧卡片迁移后仍按整文件方式检查。
- 先保持“不存依据正文”的边界。如果定位方案确实需要存储上下文文本，必须另写数据设计，说明内容、大小、保留期限和导出影响，再决定是否采用。

验收条件：目标片段修改能发现；片段外修改在定位仍有效时不误报；插行、删除、重复文本、编码变化和文件缺失有明确结果；whole-file 与片段混合卡片继续遵守原有汇总优先级与复核门槛。

迁移与回退：迁移前保留 schema 1 完整备份；原子迁移且失败保留原文件；旧版遇到 schema 2 应拒绝写入。回退通过恢复迁移前备份完成，必须说明回退会丢失迁移后的新增记录，因此回退前另存 schema 2 副本。禁止直接降 schema 字段假装兼容。

当前只有文件哈希，没有过去的依据正文，**无法凭哈希生成历史文本 diff**。若以后做 Git 对比，必须验证文件确实受 Git 跟踪、基线提交存在且内容与捕获基线一致；该能力不属于本版默认承诺。

## 6. 暂不排进上述必做范围的候选功能

| 候选 | 为什么可能有价值 | 进入具体版本的条件 |
| --- | --- | --- |
| 标签、类型和保存的筛选 | 借鉴 Evidence Ledger，改善卡片分类 | 试用者在现有搜索/意见筛选下仍难找到卡片；先定义最小字段、数量限制和 schema 迁移，再排期 |
| 选中助手消息直接建草稿 | 减少复制粘贴，借鉴 Synapse 的原生联动 | 宿主有稳定公开的选择/消息操作接口；只处理用户明确选中的内容，不读取整段会话；精确消息来源与 actor 会话要分开建模 |
| 结构化备份导出和恢复向导 | 降低手动复制 JSON 的门槛 | 实际出现恢复困难；先做导出/校验/预览，再考虑恢复。任意跨项目导入、卡片合并和自动信任旧检查不进入首版 |
| 磁盘草稿 | 刷新后仍能继续录入 | 用户确实频繁丢草稿；定义显式选择、项目隔离、过期清理与隐私边界；优先宿主存储，不能依赖会随端口变化的浏览器 origin |
| 完整英文 UI | 扩大公开插件可用范围 | 有使用需求且宿主 i18n 接口稳定；跟随宿主语言，不另设冲突的语言开关 |
| 打开项目时提示检查 | 降低忘记复核的概率 | 证明手动入口不足；先提供可关闭的提示，实际检查仍有范围与预算，不默认后台写入或唤醒 Agent |

持续保留现有边界：不自动判断结论真假，不自动执行测试，不全量抓取对话，不自动抓 URL，不做云同步、多用户权限系统、向量数据库或跨 Host 并发写入承诺。宿主已有的自动化、团队调度和上下文统计，优先通过公开接口衔接。

## 7. 维护与发布办法

### 7.1 兼容支持策略

- 目标是长期维护少量经过验证的宿主组合：一个主要组合和一个候选组合；旧组合退出支持前写明最后可用插件版本与原因，不突然删除说明。
- 每次宿主 Release 先读变更、定位本插件实际使用的接口，再安排隔离配置测试。不要直接升级用户日常 Desktop。
- 支持清单同时区分 Host 与 Client、Web 与 Desktop、源码测试与实际 tgz 安装。源码编译成功不等于桌面验收完成。
- 只有测试结果支持时才修改精确依赖范围；不为消除安装提示而删除 peerDependencies 或用无限制通配版本。

### 7.2 日常维护节奏

建议每周人工检查一次宿主发布和本项目问题，每个迭代约 20%–30% 时间留给复现、兼容与文档。这里只是维护安排建议，本次没有创建自动监控或定时任务。

问题处理顺序：数据/权限/错误复核 → 支持组合加载失败 → 核心流程受阻 → 使用不便 → 新功能。先记录宿主、插件、平台、最小复现、期望与实际，再决定补丁。缺陷修复增加能复现该缺陷的回归，不以提高测试数量为目标。

维护责任可由同一人承担：用户确认需求和真实体验，开发辅助完成实现与检查，维护者决定发布。不要因为计划表写了“测试、发布、维护”就假设已经有三名成员或承诺响应 SLA。

### 7.3 每次发版检查

1. 用本次提交执行 `npm run check`；延续现有实际 tgz 安装、卸载、重装和保留数据检查。
2. 仅对受影响的 UI/宿主组合补充真实回归；主次功能、主题、窄栏、键盘/输入法和与其他插件共存需要对应证据。
3. 验证升级与回退；如有 schema 变更，单独执行迁移、失败中断和恢复测试。
4. 从验收的同一提交生成安装包；npm 与 GitHub 使用同一份包并提供 SHA-256；发布后验证下载内容和实际加载版本。
5. Release 写清新增、修复、支持组合、已验证范围和已知限制；失败的候选兼容验证不被遗漏，也不混入支持声明。

现有 CI 和发布制度是基础，这些条目用于扩展与落实，不是重新搭建一套流水线。研究与计划不构成发布授权；本次没有替用户发布新版本。
